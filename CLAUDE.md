# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A WorldSkills 2022 TP53 Day 2 ("Micro Services on AWS EKS") **practice starter kit** — it
reproduces what a competitor's AWS account looked like when the competition started (baseline
IAM + a bastion host), not a solution to the challenge. The original spec is
`WSC2022SE_TP53_Day2_actual_en.pdf`; read it before making non-trivial changes.

This distinction governs almost every design decision in the repo and must be preserved:

- **Terraform provisions ONLY the baseline** a participant is given: `UnicornPolicy` /
  `AutoScalerPolicy` / `ELBControllerPolicy` / `EFSPolicy` (created but deliberately left
  **unattached** — the spec says the security team gave no instructions on this, so wiring
  them up is part of the challenge), `EKSClusterRole` / `EKSNodeRole` (only the AWS-mandatory
  managed policies attached, nothing extra), `TeamRoleInstanceProfile`, and a bastion EC2
  instance (SSM Session Manager access only — no SSH key pair, no inbound SG rule, ever).
- Terraform must **never** provision the participant's actual solution: EKS cluster, node
  groups, RDS, ElastiCache, EFS, the app's S3 bucket, AppConfig application, ALB/Load Balancer
  Controller, or any Kubernetes resources. If a change starts to add one of these, stop —
  that's out of scope by design.
- `services/root` and `services/stub` are **from-scratch practice replacements** for the
  proprietary Go binaries described in the spec, not the real binaries and not a
  reverse-engineering of them. Don't try to make them byte-identical to anything; they just
  need to satisfy the documented interface (see Architecture below).

## Commands

### Go services (`services/root`, `services/stub` — independent modules)

```bash
cd services/root && go build -o /tmp/root . && go vet ./...
cd services/stub && go build -o /tmp/stub . && go vet ./...
```

No test suite exists in either module. Both binaries support `--help`; use it plus a manual
`curl` against `GET /` (expect HTTP 200) as the smoke test — see `scripts/verify.sh` for the
pattern (spins up both binaries with a throwaway local config and curls them).

### Build / package / verify (from repo root)

```bash
./scripts/build.sh     # compiles both services for linux/amd64 into dist/
./scripts/verify.sh     # builds, then runs --help + GET / checks against both binaries
./scripts/package.sh    # runs build.sh, assembles the rest of dist/ (configs, schema.sql,
                         # refund-notifier.sh, dist/README.md), and builds Docker images if
                         # Docker is available
```

`dist/` is entirely generated by `scripts/package.sh` — never hand-edit files under it;
edit the source under `services/`, `config/`, `database/`, or `scripts/refund-notifier.sh`
and re-run the script. There is no `.gitignore` in this repo, so `dist/` (including the
compiled binaries) is currently untracked-but-not-ignored; be deliberate before `git add`-ing it.

### Terraform (`terraform/`)

```bash
cd terraform
terraform init
terraform fmt -recursive
terraform validate
terraform plan
```

`terraform plan`/`apply` make real AWS API calls (the AMI data source, caller identity, etc.)
and `apply` creates real billable resources — never run `apply` without the user's explicit
go-ahead. `terraform validate` and `plan` are safe to run freely for verifying changes.

### Docker Compose (local practice stack, no AWS required)

```bash
docker compose -f docker/docker-compose.yaml up --build
curl localhost:8080/   # root
curl localhost:8081/   # stub
```

Uses `config/*.local.json` (Redis wired to the compose network; S3/Secrets Manager left
disabled since those need real AWS) — different from `config/*.example.json`, which documents
the AppConfig payload shape and is what ships in `dist/`.

## Architecture

### Config loading (`config.go` in each service)

Both binaries resolve configuration in this order: if `--appconfig-application` /
`--appconfig-environment` / `--appconfig-profile` (or the matching env vars) are all set, fetch
live from AWS AppConfig via `appconfigdata` (`StartConfigurationSession` +
`GetLatestConfiguration`); otherwise fall back to reading a local JSON file (`--config`, default
`config.json`) — the fallback exists purely for local testing (docker-compose, `verify.sh`), not
as a documented competition path. `--port` / `PORT` overrides whatever the resolved config says.

### Service dependencies

- `root`: Redis (`redis.go`, cache-through on `GET /unicorns/{id}`), filesystem cache path, S3
  (`storage.go`, refund records via `POST /refund`).
- `stub`: Secrets Manager (`database.go`, resolves rotated MySQL creds from `DBSecretArn`),
  MySQL/RDS (the `unicorns` table — see `database/schema.sql`, name/columns are fixed by the
  spec), filesystem cache, S3 refund records — same `storage.go` pattern as `root`.
- Both expose `GET /` and `GET /healthz` (spec's health check, must return 200), and
  `POST /refund {"order":"<uuid>"}` which persists the order UUID as an S3 object (key AND
  body = the UUID) — this is the "Request Exception Logs" flow from the spec's architecture
  diagram, and the interface a Request Exception Handling caller (see below) issues against.

### Terraform structure

`iam.tf` is the core file — read its header comments before editing. `versions.tf` /
`providers.tf` / `variables.tf` / `outputs.tf` / `main.tf` are standard scaffolding.
`baseline.tf` provisions a *minimal* VPC (one public subnet, IGW) solely so the bastion has a
place to live — it is explicitly not a model for the participant's own VPC design, and
`create_baseline_network` lets it be skipped in favor of an existing VPC. `bastion.tf` is the
EC2 instance + user-data (dev tooling install); it must never gain a public SSH path. The AWS
Load Balancer Controller's IAM policy is vendored as a static JSON file at
`terraform/policies/elb-controller-policy.json` (AWS's own published reference policy) rather
than inlined, since it's long and stable — reproduced from memory, so diff it against the
current upstream policy before relying on it for a real run.

### `scripts/refund-notifier.sh`

Implements the spec's "Request Exception Handling": polls an S3 bucket for refund-record
objects (reading the order UUID from each object's *content*, not its key, per the spec's
wording), and POSTs `{"id": "<PARTICIPANT_ID>", "order": "<uuid>"}` to an audit endpoint,
deduplicating already-reported keys in a local state file. `--bucket`, `--id`, and `--endpoint`
are all required — there's no baked-in default endpoint, because the payload shape here
(`id` + `order`) is a simplified contract designed to pair with a companion GameDay-simulator
project, not the literal `{"game","team","order"}` example from the original spec PDF. If you
ever need to target the real WorldSkills audit endpoint instead, the payload shape will need to
change back.
